# Отправка оценённых вакансий в job-apply-tracker — план реализации

> **Для агентов-исполнителей:** ОБЯЗАТЕЛЬНЫЙ САБ-СКИЛЛ: superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans — выполнять план задача за задачей. Шаги размечены чекбоксами (`- [ ]`).

> Перевод [английского плана](2026-10-25-tracker-push.md). При расхождениях главный — английский.

**Цель:** после каждого рана (и при каждой 15-минутной проверке, пока что-то ждёт отправки) job-ai-assist
доставляет каждую оценённую вакансию в API приёма job-apply-tracker и повторяет, пока её не примут, никогда
не замедляя и не ломая ран и отчёт в Telegram.

**Архитектура:** ports & adapters, как во всём репозитории: порт `VacancyTracker` в `core/ports.py`,
адаптер на httpx в `local_connectors/tracker.py`, таблица очереди (outbox) в существующем SQLite-хранилище,
сборка и цикл отправки в `app/`. Данные для отправки собираются в момент отправки из таблицы `vacancies`,
поэтому переоценка (грубая → финальная) уходит с самой свежей оценкой.

**Стек:** Python 3.12, httpx (уже закреплён), SQLite, pytest с `httpx.MockTransport` (без сети в тестах).

**Спека:** репозиторий job-apply-tracker, `docs/superpowers/specs/2026-10-24-stage2-push-api-design.md`,
разделы «A1. API приёма» (контракт) и «Часть B».

## Глобальные ограничения

- Контракт: `POST {TRACKER_API_URL}/api/v1/vacancies/`, заголовок `Authorization: Token <ключ>`, тело
  `{"vacancies": [...]}`, **≤ 200 элементов** за запрос; ответ `{"results": [{"external_id", "status":
  "created"|"updated"|"invalid", "id"?, "errors"?}]}` в порядке запроса.
- Поля элемента: `external_id` (ID оффера), `title`, `company` (может быть пустым → трекер возьмёт
  «Unknown company»), `url`, `location`, `salary` (`salary_text` карточки), `score` (0–100), `score_stage`
  (`rough`|`final`), `reasons_en`, `reasons_ru` (списки, пустые строки выбрасываются), `first_seen_at`
  (ISO 8601 с часовым поясом).
- В очередь попадают только оценённые: статусы `scored-rough`, `scored-final`, `repost-of-*`. `score_stage`
  у `repost-of-X` берётся из статуса X (`scored-final` → `final`, иначе `rough`).
- Принятые (`created`/`updated`) уходят из очереди. `invalid` логируются на WARNING с ошибками и уходят из
  очереди (без повторов). Ошибка связи / ответ не 200 → всё остаётся в очереди.
- Настройки только из окружения: `TRACKER_API_URL`, `TRACKER_API_TOKEN`. Нет любой → отправка выключена,
  одна строка INFO. Токен никогда не печатается, не логируется и не попадает в командную строку;
  `install_redaction(token)` закрывает логи. `.env` правит пользователь сам (правило репозитория: Claude не
  читает `.env`).
- Проблема с трекером никогда не роняет ран и не задерживает Telegram: сначала доставка в Telegram, потом
  отправка в трекер, каждая в своём try/except.
- compose: `daily-run` подключён к сети `default` и к сети, объявленной как `name: job-net` (не external),
  поэтому контейнер стартует и с трекером, и без него.
- Правила репозитория: TDD, `py -3.12 -m pytest tests/ -q` зелёный без сети; никогда `git add -A` (WIP
  пользователя в блокноте и неотслеживаемые `CLAUDE.md`/`.claude/` не трогаем); стиль коммитов — простое
  повелительное предложение.

## Фокус ревью

1. Трекер недоступен днями → очередь растёт и уходит пачками по 200, когда он вернётся; ничего не теряется и
   не дублируется — задача 3.
2. Грубая оценка позже заменена финальной → вакансия снова в очереди, трекер получает финальную — задача 1.
3. Трекер отвечает 401 (неверный/перевыпущенный токен) → всё в очереди, одно WARNING за проверку, ран и
   Telegram продолжают работать — задача 4.
4. Первое подключение → весь накопленный архив ставится в очередь ровно один раз, в том числе после
   перезапусков контейнера — задача 1.
5. Ответ, где результатов меньше, чем отправленных элементов → несопоставленные остаются в очереди, а не
   помечаются доставленными — задача 3.

### Задача 1: Очередь в хранилище

**Файлы:** изменить `app/store.py`; тесты `tests/test_store.py`.

**Производит:** таблица `tracker_outbox(offer_id, queued_at)`; `Store.record(...)` ставит оффер в очередь
(upsert с обновлением `queued_at`) при статусах `scored-rough`, `scored-final`, `repost-of-*`;
`Store.tracker_pending(limit)` — строки очереди вместе с данными из `vacancies` и статусом оригинала для
перепостов, сначала самые старые; `Store.tracker_done(offer_ids)`; `Store.queue_tracker_backlog() -> int` —
ставит в очередь все уже оценённые один раз (флаг `tracker_backlog_queued` в `bot_state`).

- [ ] **Шаг 1: Падающие тесты:** оценённая — в очереди; отсеянная — нет; финальная оценка снова ставит
  грубую в очередь; перепост несёт статус оригинала; доставленные уходят из очереди; порядок «сначала старые»
  и лимит; архив ставится один раз даже после переоткрытия базы.
- [ ] **Шаги 2–4:** FAIL → реализация → весь набор зелёный.
- [ ] **Шаг 5:** Коммит «Queue every scored vacancy for the tracker in the store».

### Задача 2: Клиент трекера (порт + адаптер)

**Файлы:** изменить `core/ports.py`; создать `local_connectors/tracker.py`, `tests/test_tracker_client.py`.

**Производит:** порт `VacancyTracker.push(vacancies) -> results`; `TrackerClient(base_url, token, client=None)`,
таймаут 30 с, `TrackerError(message, status)` при ошибке связи и ответе не 200, токен вычищен из текста,
исключение не цепляется.

- [ ] **Шаг 1: Падающие тесты:** клиент соответствует порту; запрос идёт на `/api/v1/vacancies/` с заголовком
  токена и телом `{"vacancies": [...]}`; лишний `/` в адресе не мешает; результаты возвращаются; 401 —
  ошибка со статусом; при сетевой ошибке токена в тексте нет.
- [ ] **Шаги 2–4:** FAIL → реализация → зелёный.
- [ ] **Шаг 5:** Коммит «Talk to the tracker's ingest API through a port».

### Задача 3: Синхронизация — данные, пачки, результаты

**Файлы:** создать `app/tracker_sync.py`, `tests/test_tracker_sync.py`.

**Производит:** `to_payload(row) -> dict` (элемент контракта из строки очереди); `sync(store, tracker,
batch_size=200) -> SyncResult(sent, accepted, invalid)` — пачка → отправка → принятые и невалидные убрать из
очереди (невалидные залогировать) → следующая пачка; результаты сопоставляются по позиции и проверяются по
`external_id`; без результата — остаётся в очереди; `TrackerError` пробрасывается.

- [ ] **Шаг 1: Падающие тесты** с поддельным трекером: точный набор полей; стадия перепоста от оригинала;
  пустые причины выброшены; принятые уходят; невалидные логируются и не повторяются; неудачная отправка
  оставляет всё; 450 штук уходят пачками 200, 200, 50; короткий ответ оставляет несопоставленные в очереди.
- [ ] **Шаги 2–4:** FAIL → реализация → зелёный.
- [ ] **Шаг 5:** Коммит «Send queued vacancies to the tracker in batches and keep what was refused».

### Задача 4: Встраивание в ежедневный цикл, сеть compose

**Файлы:** изменить `app/main.py`, `compose.yaml`, `.env.example`; тесты `tests/test_main.py`.

**Интерфейсы:** `tracker_settings()`; `push_to_tracker(config, tracker)` — никогда не бросает исключение, при
сбое одно WARNING «will retry on the next check»; в `main()` при наличии настроек — `install_redaction(token)`,
`TrackerClient`, `queue_tracker_backlog()` один раз при старте и `push_to_tracker` после доставки в Telegram на
каждом проходе цикла (и при `--once`); без настроек — одна строка INFO. compose: сети `default` и `jobnet`
(`name: job-net`). `.env.example`: `TRACKER_API_URL=http://job-apply-tracker:8000` и пустой `TRACKER_API_TOKEN=`.

- [ ] **Шаг 1: Падающие тесты:** без настроек отправка выключена; законченный ран отправляется в трекер;
  сбой трекера не роняет ран (код выхода 0, предупреждение, Telegram раньше); токен не попадает в лог.
- [ ] **Шаги 2–4:** FAIL → реализация → зелёный.
- [ ] **Шаг 5:** Коммит «Push to the tracker after every check without letting it hold up the run».
